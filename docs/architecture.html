הקשר מערכתי (System Context)

משתמשים: מועמד/ת (employee), מעסיק/ה (employer), מנהל/ת (admin). המערכת רצה על Vercel (Next.js 16, Node runtime ב־API), עם Postgres (Supabase או DATABASE_URL ישיר), Google OAuth (Auth.js / next-auth v5), ו־Google Gemini דרך Vercel AI SDK (@ai-sdk/google).

רצף: תור שיחה (Chat Turn)

ב־src/app/api/chat/route.ts: לאחר אימות (assertActor), מועמד חייב קו״ח (employeeHasCv). עם מפתח Gemini — שני קריאות במקביל: stream*Reply (טקסט, temp 0.7) ו־extract*Patch (structured, temp 0.25). התשובה מוזרמת ללקוח כ־delta מדומה (typing); בסיום — apply*Turn ב־application (מיזוג כרטיס + conflicts).

רצף: pipeline קו״ח (שני מעברים)

runCvExtraction ב־cv-extraction.ts: Pass A (עובדות מפורשות, temp 0.1, עד 4096 tokens), Pass B (inferences עם evidence, temp 0.2, עד 12 פריטים). טקסט נחתך ל־~14k תווים. ללא מפתח — heuristic. לאחר ניתוח — scheduleCandidateEmbeddingRefresh + scheduleMatchRebuild ב־after().

רצף: התאמה היברידית + כיול

rebuildMatches סורק כל job × employee, מדלג על matches שכבר approved/rejected. ציון דרך scoreCandidateForJob: מצב MATCHING_MODE (ברירת מחדל hybrid), משקלות 80/20 semantic/rule, סף תור MATCHING_QUEUE_THRESHOLD=0.6.

Embeddings: שלושה segments (card-embedding-text.ts) — לא שכר/מיקום/ch must-haves בוקטור. דמיון קוסינוס מכויל: calibrateCosineSimilarity עם רצפה 0.75; segments ריקים מדולגים. Must-have gate + גמישות (applyMustHaveGate, bilingual aliases). אם אין וקטורים — fallback לכללים בלבד.

החלטות הנדסיות ופשרות

למה שתי קריאות LLM בשיחה?

  • Streaming טקסט ללא schema — חוויית משתמש טובה; generateObject נפרד — JSON אמין לכרטיס. temp גבוה יותר לשיחה (0.7), נמוך לחילוץ (0.25).
  • עלות: ~2× קריאות למעבר; מוצדק כי patch שגוי פוגע בהתאמות.

Conflicts במקום overwrite

שומר אמון ומקור (קו״ח vs שיחה). מעסיק/מועמד יכולים ליישב later; prompts כוללים pending conflicts.

Grounding ב-CV

Pass A מחייב עובדות מפורשות; Pass B דורש evidence + confidence; inferences נשמרים כ־pending עד אישור.

Fallback heuristic

ללא GOOGLE_GENERATIVE_AI_API_KEY — intake/heuristic ו־matching rule-only; האפליקציה נשארת usable.

למה לא embed שכר/מיקום?

ערכים נומריים/גיאוגרפיים לא stable בוקטור; נשארים ב־scoreMatch (textScore, penalties) ו־must-have gate.

בקרת עלות

  • ai_usage + slice של 200 רשומות אחרונות בזיכרון store.
  • Rebuild matches debounced; embedding refresh serialized (__shidukhEmbeddingRefreshRunning).
  • enrichReasonWithAi — מוגדר אך לא מחובר ל-rebuild (הערה בקוד).

גישה ופרטיות

  • ברירת מחדל: Auth.js session + התאמת userId; אופציונלי ALLOW_DEMO, dev login, allowOpenAuth לפיתוח.
  • CV blobs בטבלה נפרדת; גישת admin מוגבלת לנתיבי admin.

Observability

Health routes (/api/health/db|ai|auth), לוג שגיאות Gemini + degraded flags ב־final chat frame. אין OpenTelemetry מוטמע ב-POC.

מגבלות ידועות ומפת דרכים

  • RAG על תיאורי משרה מלאים — לא קיים; matching על כרטיס מstructured.
  • MCP server לכלי התאמה — לא ב-production; eval offline ב־npm run eval:matching.
  • LLM rerank — לא מיושם; דירוג = score יחיד.
  • תיוגים ממשוב אמיתי — בדרך; holdout v1 + import labels.
  • Cross-language + flexibility — עדיין good-misses ב-eval; role-calibrated floor ומילון must-have מ mitigates.
  • Overfitting: hyperparameters כוילו על 90 זוגות train — דווח train/holdout נפרד ב-eval.
